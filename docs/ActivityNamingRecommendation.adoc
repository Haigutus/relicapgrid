== Activity Naming Recommendation 

=== Purpose

The `prov:wasGeneratedBy` property identifies the activity that generated a dataset entity.

As dataset entities may contain instances conforming to one or more profiles, and the same profile may be generated in different operational or business contexts, the activity naming shall not be derived solely from profile names.

The purpose of the activity naming convention is to provide:

* a unique and stable identifier for the generating activity;
* a consistent and controlled vocabulary for provenance metadata;
* human-readable identifiers;
* identifiers that are interpretable by automated and AI-assisted tooling;
* sufficient contextual information to distinguish datasets generated for different purposes.

The activity naming represents the generating action, not the dataset structure.

=== Naming Structure

The recommended naming structure is:

[source]
----
<ActivityType>-<Profile>[-<Process>][-<TimeHorizon>][-<Run>]
----

Where:

* `ActivityType` is mandatory;
* `Profile` is mandatory;
* `Process` is optional;
* `TimeHorizon` is optional;
* `Run` is optional.

Elements shall appear in the defined order.

=== Naming Elements

[cols="1,1,4",options="header"]
|===
| Element | Cardinality | Description

| ActivityType
| 1
| The type of activity that generated the dataset entity.

| Profile
| 1
| The profile or dataset type generated by the activity.

| Process
| 0..1
| Optional business or operational process context.

| TimeHorizon
| 0..1
| Optional temporal planning or operational horizon.

| Run
| 0..1
| Optional identifier for repeated executions of the same process.
|===

=== Activity Types

The following controlled vocabulary shall be used for `ActivityType`.

[cols="1,4",options="header"]
|===
| Activity Type | Definition

| StructuralRepresentation
| Creation of structural, topological, or functional representations of the power system, including detailed models, reduced representations, equivalents, and abstractions.

| AssumptionDefinition
| Creation of assumed operational conditions used as input to studies, simulations, planning, or operational analysis.

| ScheduleDefinition
| Creation of planned future operational schedules, allocations, commitments, or declared availability information.

| AnalyticalComputation
| Creation of datasets containing calculated analytical results derived from deterministic or algorithmic processing.

| MeasurementAcquisition
| Creation of datasets originating from direct observation, telemetry, metering, or real-time acquisition.

| Assessment
| Creation of datasets resulting from evaluation or analysis of submitted requests, system conditions, or operational scenarios.

| Verification
| Creation of datasets representing validation or conformance checking against specifications, business rules, or semantic constraints.

| Request
| Creation of formal request datasets intended to trigger assessment, approval, or further business processing.

| Response
| Creation of datasets responding to a prior request, submission, or assessment.

| Publication
| Creation of authoritative datasets intended for publication and reuse.
|===

=== Profile

The `Profile` element identifies the information structure and reference the primary ConformTo or dataset type generated by the activity.

Examples include:

* `EQ` - Equipment
* `SSH`
* `SV`
* `TP`
* `DL`
* `GL`
* `BD`
* `CD`
* `RD`
* `RAS`

The profile shall reflect the generated entity, not the source data.

=== Process

The `Process` element identifies the optional business or operational context.

Examples include:

* `CGM` - Common Grid Model
* `TYNDP`
* `CSA`
* `OPC`

The controlled vocabulary for processes shall be defined by the applicable implementation or business domain.

=== Time Horizon

The `TimeHorizon` element identifies the optional temporal context for the activity.

ISO 8601 duration notation is recommended.

Examples:

* `P1Y` — year-ahead
* `P1M` — month-ahead
* `P1W` — week-ahead
* `P3D` — three days ahead
* `P2D` — two days ahead
* `P1D` — day-ahead
* `PT0H` — intraday / current operational timeframe

=== Run

The `Run` element identifies repeated executions of the same activity within the same process and horizon.

Examples:

* `Run1`
* `Run2`

Compact forms may be used where agreed:

* `R1`
* `R2`

=== Naming Rules

The following rules apply:

* The activity identifier shall represent the generating activity.
* The same profile may be generated by different activity types.
* Multiple profiles may be generated by the same activity.
* The activity identifier shall not be derived solely from profile names.
* Optional elements shall only be included when needed to distinguish activities.
* Implementations shall use a consistent naming vocabulary.

=== Examples

[cols="1,4",options="header"]
|===
| Activity Identifier | Meaning

| `StructuralRepresentation-EQ`
| Structural creation of an equipment model.

| `StructuralRepresentation-EQ-CGM`
| Equipment model generated as part of the CGM process.

| `AssumptionDefinition-SSH-CGM-P1D-Run1`
| Day-ahead assumed operating state for CGM, first run.

| `AnalyticalComputation-SV-CSA-P1D-Run2`
| Analytical computation of state variables for coordinated security assessment, second run.

| `ScheduleDefinition-RAS-OPC-P1W`
| Weekly remedial action schedule definition.

| `Verification-EQ`
| Verification of an equipment dataset.

| `Request-RAS`
| Formal remedial action request.

| `Response-RAS`
| Response to a remedial action request.

| `Publication-BD`
| Publication of boundary data.

| `MeasurementAcquisition-SV`
| State variable dataset originating from measurement acquisition.
|===

=== Notes

`prov:wasGeneratedBy` identifies the generating activity and shall not be interpreted as a file naming convention.

File names and dataset titles may reuse the same identifier for consistency, but operational semantics shall be derived from metadata rather than parsing file names.
